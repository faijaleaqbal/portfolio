Flagship · 01 Campus Operations & Verified Issue Resolution

MaldaOS

Campus Operations & Issue Resolution Platform with Supabase RLS, role-based workflows, AI triage, audit logging and 3D campus visualization.

17 pages + 1 API route 165 frontend tests passing 33 AI-gateway tests passing 53 RLS policies 27 RPC functions CI: lint · typecheck · build · guards

Problem: campus issues (broken infrastructure, maintenance requests, safety hazards) get reported through informal channels, get lost, and have no verifiable resolution trail. Solution: an institutional command ledger — students file structured reports with evidence and location, department staff get dispatched work orders, and every lifecycle transition is database-enforced and audit-logged.

  • Next.js 14 App Router: 17 pages (student, report, map, 8 admin views) + 1 server-side AI triage API route
  • Supabase Postgres with 53 RLS policies across 8 migrations — direct table mutations blocked by guard triggers
  • 27 RPC functions (SECURITY DEFINER) govern every privileged write: transitions, assignments, endorsements
  • Provider-agnostic AI gateway (Groq → OpenRouter → NVIDIA → Google → deterministic fallback), server-only keys, advisory-only output
  • Fail-closed production guards: mock layer can never activate in production builds, verified by dedicated guard tests + CI
  • 3D campus twin (Three.js) + 2D Leaflet GIS map, WebGL safety fallbacks, reduced-motion support
How do you stop students modifying another student's issue?

Supabase RLS + SECURITY DEFINER RPC + database role enforcement. Roles come from profiles.role in the database — never browser metadata. Seeded demo logins are hard-blocked in production and eliminated from the client bundle at build time.

How do you keep AI triage honest?

AI output is advisory-only (category, severity, priority, summary, confidence) that a human operator accepts or rejects. The deterministic fallback is always labelled and never claims to be a model response; the core report → assign → resolve → verify workflow works with zero providers configured.

How is every action verifiable?

Every mutation writes to audit_logs (super-admin view at /admin/audit with CSV export). Status transitions are database-enforced: OPEN → ASSIGNED → IN_PROGRESS → RESOLVED → CLOSED, with a 7-day student reopen window.

Flagship · 02 Production Discord Automation Platform

Pixel-Assistor

Production Discord automation platform replacing multiple single-purpose bots — moderation, Lavalink audio, multi-chain crypto, games and utilities.

123 commands loaded 8 categories 147 tests passing Discord.js v14 SQLite + MongoDB PM2 · live 24/7

Problem: communities juggle five single-purpose bots with conflicting permissions and downtime. Solution: one hardened bot — 123 commands across 8 categories (admin 13 · crypto 4 · extra 3 · fun 3 · games 5 · moderation 52 · upi 5 · utility 38), with a pluggable storage layer and enterprise security guardrails.

  • Discord.js v14 slash-command parsing with dynamic filesystem loader (hot-reload per command, no restarts)
  • Multi-chain crypto: EVM (Polygon, Ethereum, BNB, Arbitrum, Base, Optimism), Solana SPL, Tron TRC-20, Litecoin UTXO
  • Remote Lavalink audio node — demuxing/Opus encoding offloaded, Node event loop stays fast
  • Dual-database abstraction: SQLite (better-sqlite3, WAL) default, MongoDB when MONGO_URI is set — same command interfaces
  • Security: role/member hierarchy engine, secret redaction, anti-SSRF validation, zero-eval Shunting-Yard calculator
How do 123 commands stay maintainable?

Dynamic filesystem loader + metadata contracts. The registry smoke test asserts every command exports name/execute/category and blocks duplicate aliases — 147 tests pass on every run.

How do you prevent privilege escalation?

Centralized hierarchy engine: no action against guild owners, higher roles, or the bot itself; server co-owner locked to the actual guild owner. Covered by red-team security tests.

How does it stay up 24/7?

PM2 process management with crash recovery, background reminder/timer pollers, auto-mod rate limiting — running live on this host right now (pixel-discord-bot: online).

Flagship · 03 Private Local RAG Document Assistant

Readstacks

Private local RAG document assistant — per-user isolated vector search, multi-provider fallback, JWT-secured, streaming chat. Live now.

7 doc formats 10 tests passing SSE streaming JWT HttpOnly Docker Compose Live demo

Problem: RAG demos either ship your documents to a third-party SaaS or lock you to one cloud vendor. Solution: local-first, multi-tenant RAG — upload PDF/DOCX/TXT/MD/XLS/XLSX/CSV and chat with private, cited answers. SQLite + Vectra indexes are namespaced per user, so cross-user leakage is structurally impossible.

  • Hybrid retrieval: MiniSearch BM25 keyword + Vectra cosine vector, fused at query time
  • Token-bucket fallback engine: Gemini → Groq → NVIDIA NIM → local Ollama, with mid-stream SSE failover
  • Paragraph-aware chunking with page citations ([doc.pdf p.7]) on grounded claims
  • JWT in HttpOnly SameSite Secure cookies, bcrypt hashing, signup password policy, rate-limited auth
  • One-command ops: docker compose up brings backend + local Ollama model server online
How is per-user isolation guaranteed?

Databases and vector indexes are namespaced per user on the host they own; transactional uploads roll back files, metadata rows and vector entries atomically — never orphaned chunks.

What happens when a provider dies mid-answer?

The backend re-opens the SSE stream against the next provider in AI_PROVIDER_ORDER and the UI keeps rendering tokens — chat never dies from a single provider outage.

Where do the tokens live?

Nowhere in localStorage. JWT travels in HttpOnly cookies; auth endpoints are express-rate-limit throttled against credential stuffing.

Flagship · 04 Full-Stack Web & AI Microservices

Picfix

59-page image & PDF processing suite — exam photo resizing, PDF engine, and local open-source AI microservices with queued workers.

59 tool pages 12 API route groups 11 controllers Sharp pipeline BullMQ + Redis FastAPI AI service

Problem: government exam portals (SSC, UPSC, Passport, PAN) reject photos on dimension or file-size grounds, and PDF/image tools either cost money or upload your documents to someone else's cloud. Solution: a privacy-first suite — 59 tool pages covering image manipulation, calibrated KB compressors, a full PDF utility engine, and local AI (background removal, OCR) with zero paid cloud subscriptions.

  • Next.js 14 App Router frontend paired with an Express API gateway (12 route groups, 11 controllers)
  • FastAPI AI microservice: rembg/U2Net segmentation, EasyOCR, MediaPipe, OpenCV — models held in memory
  • BullMQ + Redis async image workers with inline timeout handling and shared-connection lifecycle
  • Sharp processing pipeline, Multer binary streams, node-cron temp-file hygiene
  • Calibrated target-size compressors (20KB–500KB images; 100KB–1MB PDFs) and PDF password unlocker
How do heavy AI jobs avoid blocking the API?

BullMQ queue + Redis-backed workers absorb image jobs asynchronously; retries are handled inline with AI_TIMEOUT semantics instead of blind queue retries.

How do exam specs stop being guesswork?

Algorithmic dimension, aspect-ratio and strict KB compressors for SSC CGL, PAN and passport requirements — built from the actual rejection rules, not generic resize sliders.

What keeps it abuse-resistant?

Redis-backed rate limiting (rate-limit-redis), trust-proxy hardening (covered by unit test), and cron-purged temp buffers so disk never accumulates uploads.

Flagship · 05 Autonomous AI Agent & Model Context Protocol

Alya

Autonomous Hinglish AI assistant on Telegram — Rasa NLU plus Groq fallback, 40-skill registry, MCP tool servers, OAuth workspace pipelines. Live on Telegram.

40-skill registry 41 Rasa intents 494 test functions Rasa 3.6 + Groq GitHub + OpenCode MCP Live on Telegram

Problem: personal assistants either answer trivia or execute tools — rarely both, and almost never in Hinglish with real workspace access. Solution: a dual-tier conversational agent — Rasa Core/NLU for intent classification, a custom action server for execution, Groq LLM for generative fallback, and MCP servers for headless tool use — across 40 registered skills.

  • Dual-tier runtime: Rasa agent (port 5005) decoupled from async action server (port 5055)
  • 40-command registry with planner metadata layer — unknown skills resolve to None, never hallucinated
  • MCP clients for official GitHub MCP (port 4097) and headless OpenCode MCP (port 4096)
  • Groq hardware-accelerated inference as conversational fallback when NLU rules need generative reasoning
  • Document synthesis engines (ReportLab PDF, openpyxl, python-docx) + Google OAuth 2.0 / MS Graph pipelines
  • Nginx reverse proxy, Docker packaging, 494 test functions across the suite
Why split NLU from execution?

Rasa handles intent confidence and slot extraction while the action server executes non-blocking I/O and external APIs — slow tools never stall conversation state.

How do you stop the agent inventing tools?

The skill registry derives planner metadata from descriptions; unregistered goals return None instead of guessed actions. Authorization, container isolation and webhook-auth tests guard the boundary.

Why Groq as fallback?

Hardware-accelerated inference keeps Telegram round-trips fast when pre-trained NLU rules need generative reasoning — with Rasa intents still owning structured flows.

Flagship · 06 Web Platform & Design System

Malda Portal

62-page institutional web portal for Malda College — academics, administration, facilities — with zero runtime framework overhead.

62 HTML pages 20 root pages 19 departments 6 cells + 5 facilities Zero framework Dark/Light themes

Problem: institutional information scattered across outdated pages with no coherent navigation. Solution: a complete static portal — 62 pages spanning 20 root institutional pages, 19 academic departments, 6 administrative cells and 5 campus facilities — under one information architecture.

  • 31 root pages + 6 cell pages + 5 facility pages + 20 subject pages = 62 verified HTML pages
  • Token-based CSS custom-properties architecture — instant dark/light theming across all pages, no duplicate bundles
  • Zero client-side framework: pure HTML5, modern CSS Grid, vanilla JS — fast first render, high Lighthouse headroom
  • Multi-target packaging: Nginx, Vercel and Docker deployment configurations
Why no framework for 62 pages?

Content pages don't need hydration. Static HTML keeps hosting trivial, renders fast on low-end phones, and removes an entire class of runtime failure.

How is theming consistent at this scale?

A CSS custom-properties token hierarchy — one variable change propagates across all 62 pages without rebuilding per-page bundles.

How does it deploy anywhere?

Dual Docker alpine + Nginx configs with gzip and static-asset caching headers — the same directory serves from any static host.
